# SQL Injection Prevention in ASP.NET Core MVC (EF Core Based)

ব্যাকএন্ড অ্যাপ্লিকেশন তৈরি করার সময় একজন backend developer-এর প্রধান দায়িত্ব হলো **server ও database secure রাখা**।  
কারণ একটি backend অ্যাপ্লিকেশন সরাসরি ডাটাবেজ, সার্ভার এবং ব্যবসার গুরুত্বপূর্ণ ডাটার সাথে যুক্ত থাকে।

সাধারণত আমরা দুই ধরনের injection attack বেশি দেখি:

1. **SQL Injection**
    
2. **Command Injection**
    

এই নোটে আমরা **ASP.NET Core MVC + EF Core** ব্যবহার করে  
👉 **SQL Injection কীভাবে হয় এবং কীভাবে প্রতিরোধ করা যায়** — সেটা real-world দৃষ্টিকোণ থেকে দেখবো।

---

## SQL Injection Attack — Concept

ধরি আমাদের একটি টেবিল আছে:

```sql
CREATE TABLE Students (
    id INT IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL
);
```

আপাতত, আমাদের টেবিলে এই রেকর্ডগুলি থাকবে:
### Students

| id  | name         |
| --- | ------------ |
| 1   | Rahim Ahmed  |
| 2   | Karima Islam |
| 3   | Hasan Mahmud |
| 4   | Nusrat Jahan |
## ❌ Wrong Approach (Vulnerable Code)

অনেক beginner developer ASP.NET / C#-এ এভাবে SQL লিখে ফেলে:

```cs
var studentName = inputFromUser;
string query = $"SELECT * FROM Students WHERE Name = '{studentName}'";`
```

📌 **সমস্যা কোথায়?**

- User input সরাসরি SQL string-এর অংশ হয়ে গেছে
    
- Database এই input-কে **code হিসেবে ব্যাখ্যা করতে পারে**
    
---

## ⚠ Attack Example

হ্যাকার সব সময় , এই ফাঁকফোকর গুলা খুঁজে "**কোথায় ডেভেলপার ধরে নিচ্ছে**" . মানে আমি যে কোড টা লিখতে গিয়ে ধরে নিলাম , আমার ইউজার ভদ্র এটা করা যাবে না। মেন্টাল ম্যাপ এ সবসময় মাথায় রাখবো, যে আমার এপ্লিকেশন ব্যবহার করবে , সে একজন দুস্টু শিশু। উল্টা পাল্টা নানা ধরণের মনের মাধুরী মিশিয়ে যেকোনো ইনপুট সে দিতে পারবে। 

#### User যদি এই input দেয়:

```cs
' OR 1=1 --
```

তাহলে final SQL হবে:

```sql
	SELECT * FROM Students WHERE Name = '' OR 1=1 --'
					or,
	SELECT * from students where name = '' OR true--'
```

### কেন এটা বিপজ্জনক?

- `1=1` সবসময় **true**
    
- `OR true` → পুরো `WHERE` clause সব row-এর জন্য true
    
- Result → **সব student select হয়ে যাবে**
    

অর্থাৎ:

```sql
	SELECT * FROM Students
```

📌 ছোট ডাটায় harmless মনে হলেও  
📌 বড় ডাটাবেজে এটা **performance disaster + security breach**

```sql
	'; DROP TABLE Students --
```

👉 পুরো table delete হয়ে যাবে।

# ✅ Correct Solution (ASP.NET Core MVC + EF Core)

এখন আসি **real solution-এ**।

---

## ✅ 1. EF Core ব্যবহার করলে SQL Injection হয় না (If used correctly)

### ✔ Correct EF Core Query

```cs
var student = await _context.Students     
.FirstOrDefaultAsync(s => s.Name == studentName);

```

📌 এখানে EF Core যা করে:

- Query **parameterized** করে
    
- User input কখনোই raw SQL হয় না
    
- Database input-কে শুধু **data** হিসেবে দেখে
    

👉 **এইটাই EF Core-এর সবচেয়ে বড় security advantage**

---

## ⚠ Still Dangerous (EF Core হলেও)

EF Core ব্যবহার করেও ভুল করা যায় ❌

```cs
	_context.Students
	.FromSqlRaw($"SELECT * FROM Students WHERE Name = '{studentName}'");
```

❌ এটা আবার raw SQL  
❌ আবার SQL Injection possible

---

## ✅ Safe Raw SQL (When absolutely needed)

```cs
_context.Students     
.FromSqlRaw(
   "SELECT * FROM Students WHERE Name = @name", new SqlParameter("@name", studentName)
);
```

📌 Raw SQL + Parameterized = Safe

আগের পদ্ধতিতে **data ছিল কোডের অংশ**। এখানে data শুধু **raw data**—ডাটাবেস একে এক্সিকিউটেবল SQL হিসেবে দেখছে না।

- **Proper User Input Validation করবো**

Query পর্যন্ত পৌঁছানোর আগেই ইনপুট ফিল্টার হওয়া উচিত। মনে রাখবেন: **ভ্যালিডেশন অ্যাপ্লিকেশন লেভেলে, সিকিউরিটি ডাটাবেস লেভেলে।**

- **Database ACL (Access Control) ঠিক রাখবো**

আমরা এপ্লিকেশন এর জন্য আলাদা একটি ডাটাবেজ ইউজার ব্যবহার করবো, যার জন্য পারমিশন সেট হবে এমন—

- ✅ **DML permission** (SELECT, INSERT, UPDATE) থাকবে
    
- ❌ ~~DDL permission (DROP, ALTER, CREATE)~~ থাকবে না
    

তাহলে ধরুন কোনোভাবে ইনজেকশন ঢুকেও পড়ল, তবুও ডাটাবেস নিজেই তা এক্সিকিউট করতে দেবে না।

## Key Takeaway

সংক্ষেপে বললে

1. Parameterized query ব্যবহার করবো
    
2. ইউজার ইনপুট কখনো বিশ্বাস করবো না, সর্বদা ভ্যালিডেশন করবো
    
3. **ডাটাবেস পারমিশন মিনিমাল রাখবো**
    

এগুলোই SQL Injection এড়ানোর সবচেয়ে কমন ও কার্যকর উপায়।

পরের অংশে কথা বলবো Command Injection নিয়ে—আইডিয়া প্রায় একই, ক্ষতি আরও বড়।
