## ✅ সমস্যার মূল প্রশ্ন:

> যদি `Transaction T1` কোন data item `X` আপডেট করে (insert/update/delete),  
> আর একই সময়ে `Transaction T2` সেই `X` পড়তে (read) চায় —  
> তাহলে T2 **কি দেখতে পাবে?**

এই প্রশ্নের উত্তর নির্ভর করে ➤ **তুমি কোন Isolation Level ব্যবহার করছো**।

---

## 📊 Isolation Level অনুযায়ী আচরণ (Behavior Table):

|Isolation Level|T1 আপডেট করলে T2 কী দেখতে পায়?|Dirty Read হয়?|Phantom হয়?|
|---|---|---|---|
|**Read Uncommitted**|✅ হ্যাঁ, T1 commit না করলেও T2 read করতে পারে|✅ হ্যাঁ|✅ হ্যাঁ|
|**Read Committed**|⛔ না, T1 commit না করা পর্যন্ত T2 কিছুই দেখতে পাবে না|❌ না|✅ হ্যাঁ|
|**Repeatable Read**|⛔ না, T2 আগের মান-ই দেখবে, যতক্ষণ না T1 commit করে|❌ না|✅ হ্যাঁ|
|**Serializable**|⛔ না, T2 সম্পূর্ণভাবে ব্লক বা সিরিয়ালভাবে চলবে|❌ না|❌ না|

---

## 🧠 সহজভাবে বলা যায়:

|ঘটনা|ব্যাখ্যা|
|---|---|
|T1 write করে, T2 সেই সময় read করে|এটাকে বলে **concurrent read/write**|
|Isolation Level বলে — এই সময়ে **T2 কি T1-এর ডেটা দেখতে পারবে?**||
|যদি দেখতে পায় → **Dirty Read** বা **Inconsistent Read** হতে পারে||
|যদি না দেখতে পায় → তখন system consistency বজায় থাকে||

---

## 🔐 উদাহরণসহ ব্যাখ্যা:

### 🔸 Read Uncommitted:

- T2 → T1 এর update হওয়া ডেটা পড়তে পারে **T1 commit না করলেও**
    
- ❗ খারাপ → **Dirty Read**
    

### 🔸 Read Committed:

- T2 → T1 এর update পড়তে পারবে **শুধু যখন T1 commit করে**
    

### 🔸 Repeatable Read:

- T2 বারবার read করলে **একই মান** দেখবে
    
- কিন্তু **নতুন insert (phantom rows)** দেখতে পেতে পারে
    

### 🔸 Serializable:

- সবচেয়ে কড়া নিয়ম
    
- সবকিছু এমন behave করে যেন সব transaction **একটার পর একটা serially চলছে**

## 🎯 Bottom Line:

> Isolation Level তোমাকে সিদ্ধান্ত নিতে দেয় ➤  
> "একাধিক transaction একসাথে চলার সময়, তারা কীভাবে একে অপরের ডেটা read/write করতে পারবে?"

এটা ঠিক করার মধ্য দিয়েই **Consistency এবং Concurrency-র মধ্যে একটা ব্যালেন্স তৈরি হয়।**
